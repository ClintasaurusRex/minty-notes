### Backup-safety remediation (November 15, 2026, after the independent audit returned FAIL)

The audit of the file-name change found that retention treated file-name times and modification times as proof of creation order (H1), counted any snapshot-named file as a recovery point (H2), could overwrite or delete another program's file around a name collision or failed write (M1), could suspend cleanup indefinitely after a future-dated name (M2), and had an intermittent folder-browser focus failure (M3). All five were reproduced before fixing: the new regression tests fail against the audited logic (16 of 18 retention tests; the H2 tests fail because the working backup is actually deleted) and the new focus test failed deterministically.

- **H1 + H2 (fixed): retention by a verified ledger.** New device setting `backupLedger` (no `DB_VERSION`/`FORMAT_VERSION` change; older apps ignore it). Each archive passes `readArchive` before it is written; the written file is read back and must match its SHA-256; the snapshot is then recorded with the next `seq` in **one IndexedDB transaction that also checks the editor-owner token** (`Repository.updateSettingAsOwner`, `WorkspaceStore.updateSettingAsOwner`). A snapshot is removed only if its bytes still match its ledger hash (ownership) and 10 later-recorded snapshots re-verify by full hash and are unchanged (size + modification time) just before the removal, with ownership confirmed. Clocks, zones, names and modification times never decide order. Unrecorded files (pre-ledger versions, copies, other browsers, interrupted writes) and changed/unreadable files are never deleted.
- **M1 (fixed within the platform's limits):** `writeFolderFile` no longer deletes anything on failure (it reports the name it may have left; that file is never counted or pruned) and never writes over a non-empty file that appeared at the chosen name after the folder was listed (it moves on to `-2`…). A replacement of our output by another writer is caught by the read-back hash. **Not achievable with the File System Access API:** exclusive create and remove-if-unchanged. A file another program creates in the instant between the emptiness check and our close can be replaced, and a file replaced between the final hash check and `removeEntry` would be removed. Both windows need another program writing to the same snapshot name in the folder while Minty Notes is working on it. Each is short in normal use, but the browser API sets **no upper bound** on how long a write, close, read-back or removal takes (a slow disk, network drive or sync client can stretch it), so no maximum duration is claimed. Putting an unpredictable token in file names would make a collision with another program's file much less likely, but it would **not** make creation or removal atomic: the API still has no exclusive create and no remove-if-unchanged, so the same windows would exist. Not done, to keep the approved names; accepted as nonblocking for the documented one-folder-per-workspace setup.
- **M2 (fixed):** future-dated names no longer affect retention at all. When more than 10 snapshots remain after cleanup, the status stores `cleanupWarning` (counts and reasons) and Settings shows it under “Cleanup”, asking the user to delete unneeded snapshots by hand. There is no hard cap that would delete them.
- **M3 (product defect, fixed):** `FolderBrowser` restored focus in `requestAnimationFrame`, which can run before React commits `busy = false`; the button is then still `disabled` and cannot take focus. Focus requests are now state applied in an effect after the commit. The new test forces that frame order and delays every directory operation; it failed on the old code (focus stayed on the page body) and passes 10/10 repeats.
- **Owner-visible consequence:** snapshots written before this change (0.4.x UTC names, and 0.5.0 builds before today) are not in any ledger, so they are **kept until deleted by hand**. Settings shows the cleanup warning until the folder holds at most 10 snapshots. A shared backup folder no longer loses another workspace's snapshots; each workspace keeps the others' files and keeps the warning.
- **Tests added/changed:** new `src/backup/retention.test.ts` (19): clock rolled back a day and corrected; zone changes with missing, rewritten and backwards modification times; same-minute bursts and a reused freed name; nine corrupt/empty/truncated files; nine recorded backups later damaged with the same size; a damaged old backup; a self-check failure; a name taken after listing; output replaced during the write; failed close leaving an incomplete file; a failed write where another program wrote our name; a candidate replaced during cleanup; a kept snapshot deleted/rewritten during cleanup; a takeover before the ledger update; a future-dated foreign file; a snapshot written with the clock years ahead; ledger fencing. `backup.test.ts`, `snapshotNames.test.ts` (time-based retention tests removed with that logic) and `projectExport.test.ts` were updated for the never-delete-unverified rule. Chromium: new real-OPFS retention test and updated write-failure test in `persistence.spec.ts`; new focus test in `folderBrowser.spec.ts`.
- **Checks:** `npm run check` **PASS**: build, ESLint, **405 tests in 28 files**. **Full Chromium suite: PASS, 65/65, 4.0 minutes** (63 earlier + 2 new), production build on isolated port 4294 with scratch build/results folders outside the repo. ### Human-readable backup file names (November 15, 2026, owner-approved, before the 0.5.0 commit)

- **Change:** new folder snapshots and downloaded backups are named in the computer's local date and 24-hour time without seconds: `minty-notes-backup-20261115-1334.zip`; a second backup in the same minute gets `-2`, `-3`… (unchanged `uniqueName`). Old `…-HHMMSSZ.zip` (UTC) names are still recognised for restore and retention, and existing files are never renamed or modified. The before-restore safety copy keeps its UTC name (not a backup snapshot; never pruned). No change to archive contents, `FORMAT_VERSION`, `DB_VERSION`, stored status shape, ownership fencing, status reporting or the separate-workspace folder restriction.
- **Retention rewritten to not trust file-name order** (`src/backup/folder.ts`: `snapshotTime`, `listSnapshots`, `pruneSnapshots`). Alphabetical order is wrong for mixed UTC/local names, for `-2` vs the base name and `-10`, and for the hour repeated when clocks go back. Now each name is read as the range of moments it can stand for (UTC exact; local covering the minute under current zone rules, both moments for a repeated hour). A snapshot is removed only when ≥ 10 others are certainly newer, with file modification times as a veto when they contradict the names. Nothing is removed if any snapshot name lies after the new snapshot's time (clock set back, or zone moved west). Uncertain order keeps extra snapshots, which are pruned later once clearly old. The just-written file is protected; a failed write never reaches retention (unchanged). This also resolves the earlier risk “newer snapshots pruned first after the clock is set back” (Remaining risks, below).
- **Tests:** new `src/backup/snapshotNames.test.ts` (19 tests; real zone rules via runtime `TZ`): owner examples (08:00/13:34/21:45), leading zeros and midnight, local vs UTC date, safeguard name unchanged; same-minute `-2`/`-3` and a failed write in a busy minute; recognition of both formats with suffixes and rejection of look-alikes; mixed-format listing; mixed-format retention where an alphabetical prune would delete newer files; steady-state newest 10; same-minute burst; New York fall-back (repeated hour) with and without modification times; spring-forward; clock set back a day; old names ahead of the clock; Berlin → New York zone change; unreadable date never removed. Chromium (`E2E_PORT=4273`, isolated output, real browser): **62/63 passed**; the one failure was `folderBrowser.spec.ts:13` (focus after Enter on “Reconnect folder browsing”), which passed when rerun and failed 1 of 8 in a repeat run. It does not import backup code; treated as an existing timing flake, not fixed here. `git diff --check` clean. Retention, DST and clock behaviour are tested with simulated directory handles in Node; real Chrome folder pruning with mixed names was not exercised manually.
- *(Retention and limitations below are superseded by the backup-safety remediation above; names are unchanged.)*
- **Limitations:** a local name is read with the *current* zone, so after moving east, old local names look older than they are; mixed with UTC names only the modification-time veto then protects order (a folder copied without modification times could prune one of the oldest snapshots slightly out of order, never one of the newest 10 written after the move). After the clock was set far back, pruning pauses until the clock passes the newest name, so the folder can grow meanwhile. A burst of manual backups in one minute is kept until ten later snapshots exist.

### Review fixes (0.1.1)
1. **Handover refused when work cannot be saved.** The editor freezes edits and saves before releasing; if saving fails it replies "refused", keeps the lock, and keeps editing with its changes intact. A thrown save error counts as a refusal. The requester only steals from a window that never acknowledges (frozen).
2. **Ownership enforced everywhere.** A stolen lock (or a commit refused by storage) makes the window read-only, cancels queued saves and retries, and stops backups. Storage now checks an owner token on every commit and restore, so stale retries from an old window are refused. Unsaved changes are held in memory with a banner: "Edit here and save them" (saved on top of the latest data) or "Discard them".
3. **Trashed pages of deleted sections.** Deleting a section/notebook moves its trashed pages' location to the Inbox. IndexedDB migration 1 → 2 repairs existing data; version-1 backups containing the orphan now restore (the page goes to the Inbox, with a warning). Live orphans are still rejected.
4. **Backups track revisions, not timestamps.** Each commit increments a stored revision in the same transaction; each snapshot records the revision it captured, read with the archived data. The interval uses a monotonic clock within a session; a clock set backwards counts as due.
5. Also found and fixed while testing: after taking editing back, the page could briefly reload without the edit that was mid-save (held edits are now saved before reloading, and in-flight saves are overlaid).

### Held-edit recovery fix (0.1.2)
The recheck of `0f28457` found that taking editing back replayed held changes as whole stale records (a body edit also carries its page record), which could revert a newer title or resurrect a trashed page's old live location in a deleted section (and then fail backup validation). Now:
- Held changes keep the stored version they were based on, and are **merged field by field** with the latest stored data. Only fields this window actually changed are applied; newer titles, locations, Trash state, and unrelated content are preserved.
- Conflicts (same field changed in both windows), edits to records deleted elsewhere, blocked deletions, and moves into deleted sections are **not applied in place**: they go to a new **"Recovered changes" page in the Inbox**, and a message says how many.
- Regression tests (`src/store/heldRecovery.test.ts`, 7, fully awaited — no timers): the two reported cases (rename in B; trash + delete notebook in B), same-text conflict, edit to a page deleted forever, conflicting rename, non-conflicting rename alongside B's new content, move into a deleted section. The browser frozen-window test now also renames the page in B and checks A keeps B's title.

### Independent audit of 0.4.2 and its remediation (November 12, 2026)
A read-only audit by a second tool (Codex) confirmed four issues and one coverage gap. All five are fixed, with regression tests. **No stored record, store, backup, or package layout changed** (data format 4, IndexedDB 5, package version 1, app version 0.4.2); the importer is stricter and the exporter packs fewer pages.
- **Finding 1 (high) — a crafted package made the importer decompress before any check** (eight duplicate `manifest.json` entries in a 3 KB file ≈ 2 MiB of work; the cause was fflate's `unzip`, which starts unpacking entries while it walks the directory, and a separate “which kind of file is this” pass). **Fixed:** packages are now read by a strict reader written for them (`src/portable/zipReader.ts`; moved to `src/backup/zipReader.ts` and shared with backups and Word documents on November 13). It validates the whole archive structure from the directory and the fixed-size headers — end record, entry count (refused from the count alone), flags, methods, sizes, the header before each entry repeating the directory, no overlap and no unclaimed bytes — **without copying or decompressing anything**; then names (duplicates, case twins, unsafe paths) and the package layout are judged; only then is **exactly one** manifest unpacked, with a hard limit. The separate detection pass is gone; a full backup chosen by mistake is recognized from that one bounded manifest. Tests count the decompression calls: zero for the audit's eight duplicate manifests and for a duplicate of any other entry, zero for every structural refusal; a good package costs exactly two (manifest and project data), a backup one.
- **Finding 2 (medium) — a 9 MiB manifest stored with a declared size of one byte passed the size limits.** **Fixed:** a stored entry must have equal compressed and declared sizes, the directory and the entry's own header must agree, and the data regions must tile the file exactly — so a stored entry's declared size *is* its real size, proven before any data is read. Compressed entries (`manifest.json`, `project.json`) are inflated in 16 KiB steps into a buffer of the declared size and refused at the first byte beyond it, if they come out short, or if the CRC differs (since November 13: steps shrink near the declared size so at most about 1 MiB more is ever produced, and memory grows with real output); a declared size that deflate cannot reach from the compressed size is refused before inflating. The limits (1 MiB manifest, 128 MiB project data) are checked against the proven sizes for both files; `project.json` must also have exactly the size the manifest records, before it is unpacked. Nothing relies on ZIP metadata alone or on checking after extraction.
- **Finding 3 (medium) — hidden reference pages could be exported when a note linked to them.** **Fixed in `selectProject`**, the one place that decides: a page **hidden for the project** is never packaged — whether it is pinned in a damaged record, linked from a note, linked from a task, or would be suggested — and neither are its pictures and files. **Additional privacy rule from the user: a page that belongs to another project is never packaged either** (before, a direct link pulled it in as a “linked” reference). Library pages that are not hidden behave as before (pinned and linked on by default, suggested opt-in). The export dialog lists every page left out for these reasons, with the reason and where it was linked from; the summary counts come from the same selection that builds the file. Links to such pages stay in the text and arrive as unavailable links; they are never redirected. There is **no opt-in for another project's page** — a possible later design is written down in `DATA_FORMAT.md` (“Proposal for later, not built”). Tests unzip the built package and search its records and its raw bytes for the excluded pages' text, IDs, and attachment checksums.
- **Finding 4 (medium) — attachments were checked by checksum only** (arbitrary text accepted as DOCX, PNG bytes declared as SVG). **Fixed** (`src/portable/attachmentCheck.ts`): every picture must be one of the seven types the canvas accepts and its **bytes must be that type** (PNG, JPEG, GIF, WebP, BMP, AVIF by signature and first header; SVG as valid UTF-8/UTF-16 text whose root element is `<svg>`); originals of imported documents are checked with the document importer's own `detectFormat` and `checkDocxContainer` (PDF marker; a readable DOCX container with `word/document.xml` within the import limits) — no second implementation. The exporter records the type it finds in the bytes (a JPEG stored under a PNG type is packaged as JPEG; the workspace is not changed) and stops with a message naming the picture and its note if a stored picture is none of the seven types. SVG handling is unchanged: pictures are only ever shown through `<img>`, which runs no scripts and loads no outside resources, and imported text is still cleaned the same way.
- **Finding 5 (low) — the “editing during import” test edited before and after, not during.** **Fixed:** new tests hold the import's IndexedDB transaction open at a deterministic barrier (a patched `IDBObjectStore.add` that keeps the transaction alive with reads until released — no timers or sleeps), make an unrelated edit while it is pending, then release it. Verified: the edit and the import are both stored, the revision advances one step for each, undo still works on the edited page, the import can also fail at that point and the edit still saves, and a takeover by another window during the import waits for it, after which the old window is fenced and its later edit is held and reconciled as usual. **The barrier found one real defect, now fixed:** `addImportedRecords` set the save status to “Saved” when the import finished even if an edit made during the import was still being written (the data was never at risk — the status was briefly wrong). It now leaves the status to the autosave in that case.
- **Note order (the user's observation).** Root cause found: a project's notes are listed **most recently edited first** (`projectNotes`); that order is dynamic by design and documented now (`ARCHITECTURE.md`, “Order of a project's notes”). Notes with the *same* edit time had no defined order and appeared in storage order — the order of their record IDs — which is random per note, so it differed between a session and its reload and, because import assigns new IDs, between a project and its imported copy. Every note of a project made from a template has the same times, so such a project shows exactly this. **Fixed** as a small, safe correction: ties are now ordered by the note's `order` (creation sequence), then creation time, then ID; packages already carried all three, so nothing in the format changed. Regression tests: a unit round trip (template-made project → package → import, same sequence, also after reload) and a real-Chromium test comparing the two sidebars. Two differences remain **by design**: editing a note after exporting moves it to the top on that side, and reference pages that arrive as project copies are listed among the imported project's notes (they were under “References” in the original). Which of these the user saw could not be confirmed, because their workspace was not accessed. A user-chosen order is recorded for Stage 5, not built.
- Compatibility: the package layout and version are unchanged, and the strict reader accepts exactly what the app's writer has produced since the first 0.4.2 build (the ZIP writer itself was not changed), so packages from the earlier 0.4.2 build are expected to import — **not tested with a file from that build itself** (none was kept; manual check D). The known exception: a package whose picture record names a different type than its bytes is now refused with the reason and must be exported again. Backups and restore were not touched.

### Second independent audit (Codex Astra) and its remediation (November 13, 2026)
A second read-only audit verified the five fixes above and the note-order fix, and confirmed two remaining defects, both outside the package reader. Both are fixed, with regression tests on hostile and on genuine files. **No stored record, backup layout, or package layout changed** (data format 4, IndexedDB 5, package version 1, app version 0.4.2); the backup writer is untouched.

- **Finding A (high) — the workspace-backup reader decompressed before checking, and trusted recorded sizes** (`unzipSafely` in `src/backup/archive.ts`, unchanged since Stage 1). Cause: it used fflate's `unzip`, which reads the directory and starts inflating each wanted entry as it goes, without checking the headers in front of the data, overlaps, or duplicates (a later duplicate silently replaces the earlier one), and which keeps inflating past an entry's recorded size (it only stops storing the bytes). The audit's two cases: a 1,049,664-byte ZIP declaring 16 bytes in all produced 16,777,216 bytes of output; a 2,998-byte ZIP with eight compressed `manifest.json` entries was decompressed eight times. Measured here before the fix: a 1 MB entry declaring 16 bytes took **2.6 s** of synchronous decoding. **Fixed:** the package reader was generalised into **one ZIP reader for every untrusted archive** (`src/backup/zipReader.ts`, moved from `src/portable/`), with two layouts: `minty` (exactly what the app writes; packages, behaviour unchanged) and `standard` (any well-formed ZIP; backups and Word documents). In both, the end record, the directory, every header in front of the data, every entry's byte range, and overlaps are checked **before anything is unpacked**; `standard` also accepts what ZIP tools legitimately write — data descriptors, extra fields, comments, gaps, and ZIP64 records — because a backup may have been unpacked and zipped again (the old reader accepted those, and repacked backups must keep restoring). `readArchive` now: refuses a name that appears twice or an unsafe path before unpacking (unknown files are still ignored with a warning, never unpacked); limits the declared total (4 GiB, as before), `manifest.json` (64 MB, new), and `records.json` (512 MB, new — the writer first holds all records as one JavaScript string, which Chrome caps at 536,870,888 characters, so real backups stay far below this); requires the directory's `records.json` size to equal the manifest's before unpacking; unpacks one manifest, then the records, then each attachment at most once (two attachments may not share a file), stopping at the first damaged file. Unpacking itself (`entryBytes`, shared) was tightened for every caller: a compressed entry is inflated in steps that shrink as it nears its recorded size, so **it is refused within about 1 MiB of passing that size whatever its data** (before: up to 16 MiB in packages, unbounded in backups), and memory grows with the bytes really produced instead of being reserved from the recorded size. fflate's `unzip` is no longer used anywhere.
- **Finding B (medium) — a malformed DOCX passed the Word-file check** (`checkDocxContainer` in `src/import/formats.ts`, used by Import document and, since the first audit, by `originalProblem` for originals inside packages). Cause: it also used fflate's `unzip`, only to list names and declared sizes (`filter` returning false), so nothing checked that a listed part really exists: the audit's 138-byte DOCX listed `word/document.xml` at byte 1,048,576 of a 138-byte file and was imported with correct checksums. Confirmed here with the old code: accepted. **Fixed:** the check now reads the container with the shared reader (`standard` layout: every part's header inside the file and in agreement with the directory, no overlaps, nothing encrypted, no part listed twice), keeps its existing rules (`word/document.xml`, ≤ 5,000 parts, ≤ 300 MB declared, macro detection), and then **unpacks every part, bounded, to exactly its recorded size and CRC without keeping it** (`checkEntry`). Declared sizes are therefore true, so the 300 MB limit now also bounds what mammoth unpacks afterwards (before, a forged size inside a DOCX could make the converter inflate without limit). The same function serves both paths, so Import document benefits too. Compressed entries did need the bounded check: structure alone cannot prove that a part's deflate data is what its sizes claim.
- **Compatibility, tested on genuine files** (`src/test/files/`, provenance in its README): one backup written by **each release's own code** — the sources of 0.1.0, 0.1.1, 0.1.2, 0.2.0, 0.2.1, 0.3.0, 0.4.0, and 0.4.1 were exported with `git archive` into a scratch folder (no branch change) and their own store and `BackupService` wrote the files — and a backup unpacked and zipped again by Info-ZIP (three ways), 7-Zip, and Python: **13 of 13 restore completely** (content checked after a full restore, then backed up and restored again), with the old reader and with the new one, in Node and in Chromium. Every release used the same writer call (fflate 0.8.3 `zip`), checked in the history of `archive.ts` and `package-lock.json`. Word documents: the 17 Word-written test documents shipped with mammoth, a LibreOffice 24.2 document, and six repacks of it (Info-ZIP plain/descriptors/ZIP64, 7-Zip, Python streamed ZIP64, Python stored with comments): **24 of 24 accepted**, old and new, and each still converts with mammoth; the Word and LibreOffice files also import and preview in Chromium. These files use exactly the features the `standard` layout had to accept: Word's deflate-option flags and `0xA220` padding fields, LibreOffice's data descriptors, Info-ZIP's and 7-Zip's extra fields, ZIP64 records.
- **Cost:** checking a 32 MB DOCX (11 MB of XML, 32 MB of pictures) now takes about 0.3 s (Node, this machine; before: nothing was checked); reading a 122 MB backup takes 0.50 s before and after.
- **Found while doing it (not fixed; outside this assignment):** fflate's ZIP writer, which every release has used for backups, writes a wrong 16-bit entry count past 65,535 entries; a workspace with more than 65,532 attachments has therefore never produced a restorable backup (checked: a 70,000-entry archive reads back as 4,464 entries). The new reader refuses such a file as damaged rather than reading part of it. A fix needs a ZIP64-capable writer and its own review.
- Code: new `src/backup/zipReader.ts` (replaces `src/portable/zipReader.ts`), `src/backup/zipReader.test.ts`, `src/backup/archiveSafety.test.ts`, `src/backup/archiveCompat.test.ts`, `src/import/docxContainer.test.ts`, `src/test/countingFflate.ts`, `src/test/testFiles.ts`, `src/test/files/` (13 backups, 7 DOCX, README), `e2e/archiveSafety.spec.ts`; changed `src/backup/archive.ts` (reading only), `src/import/formats.ts` (`checkDocxContainer`), `src/portable/readPackage.ts` (messages now composed here; reader moved), `src/test/rawZip.ts` (other writers' features, ZIP64), `src/test/portableFixtures.ts` (`importOriginal` exported), and tests whose expectations changed by design: `backup.test.ts` (an unsafe path now refuses a backup), `zipSafety.test.ts` (a package's Word original is now verified part by part), `import.test.ts` (test title), `packageValidation.test.ts` (+2 tests).

## Known limitations
- **Backup folders must not be shared between workspaces (nonblocking, documentation only).** Every browser profile/device/installed copy needs its own backup folder. In a shared folder (including one synced to several computers), each workspace deletes only snapshots recorded in its own ledger, so it keeps the other workspaces' snapshots and shows the cleanup warning permanently; two devices can still write the same one-minute file name, and the outcome then depends on the sync service. See DATA_FORMAT.md, “Backup archive”.
- **Backup cleanup keeps what it cannot prove (by design).** Snapshots written before the ledger (0.4.x UTC names and earlier 0.5.0 builds), copied-in files, interrupted writes and changed files are never deleted automatically; Settings shows the cleanup warning until the folder holds at most 10 snapshots. Each cleanup reads about 10 × the backup size. Remaining filesystem-API limits (no exclusive create, no remove-if-unchanged, no bound on how long an operation takes) are described in DATA_FORMAT.md.
- **Backup takeover message can be misleading (nonblocking).** When `backupNow` re-checks editing ownership (before the folder write, after it, after retention, and in its error path) and the check does not succeed, the result says editing moved to another window. The check also fails when the window became read-only for another reason or when reading the stored owner token fails, so the message can name a takeover that did not happen. In the error path the original error text is kept, followed by the takeover sentence. The outcome is safe: no further folder write, pruning or status write happens. Only the wording may be wrong; the user can retry from the editing window.
- Stage 1 limitations still apply: held changes live only in that window's memory; no character-level text merge; opening a page can save re-measured text heights; undo is per page and in memory; no multi-select, guides, snapping, alt-text editor, or checklists; image bytes of deleted objects are kept; backups are built in memory; basic phone layout; folder backups need Chrome/Edge on a desktop and only run while the app is open; restore replaces the whole workspace.
- Project details, categories, tags, pins/hides, archive, and project trash are not in undo history (page Trash and project Trash cover deletion).
- Tags are on pages only (not on projects); categories are on projects, notebooks, sections, and pages.
- Search reads all stored text into memory and is rebuilt after each save; Stage 5 measurements are in STAGE5_PERFORMANCE.md. Original attachment contents are not searched — only their file names.
- Recently opened pages are per device (`localStorage`) and not in backups.
- Local file paths are copied, not opened (browsers cannot open arbitrary local paths). Dropbox links open in a new tab and need a connection.
- A project copy shares image bytes with the original (bytes never change, so the pages stay independent).
- Deleting a page forever also removes it from other projects' pins; there is no per-link history.
- An invalid due date already stored by 0.2.0 stays in this browser's workspace until the date is changed; restores clear it (with a warning).
- Two windows can each create a category or tag with the same name while one cannot save; both are kept (rename or delete one in Settings).
- In a held-edit merge, a pin in one window and a hide of the same page in the other both survive; the page then shows as pinned.
- **Stage 3:** task changes (moves, edits, deletes) are not in undo history; task deletion asks for confirmation and is permanent (no task Trash). Deleting a project forever deletes its tasks. Tasks have no recurring dates, reminders, notifications, time tracking, assignees, or calendar sync. Drag-and-drop is basic (drop on a card inserts before it; drop on a column appends) and was not browser-automated. Templates are snapshots: editing a template's content means saving a new one (rename/describe/delete only in Settings). A project template keeps file locations, equipment, and software but not customer, site, job number, contacts, dates, or task status. Template images reuse attachment bytes (never changed), like project copies. Task filters are per device (`localStorage`). Local paths are copied, never opened. Daily work logs are not built (optional later).
- **Stage 4:** Tables have no drag-to-resize columns (they size to the text box) and no cell colours; code blocks have no syntax highlighting or language label. Page links: a link to a page deleted forever stays (marked “deleted”) rather than being removed; links inside a project template still point at the original pages (not remapped to the new project's notes); backlinks are read when a page opens (not live); no page-title autocomplete inside the text beyond the picker. Markup: one editor at a time in a modal window; no multi-select, rotation, or snapping; text labels have no font choice; blur and redact areas always draw under other annotations; **the original image (and every backup) keeps redacted pixels — only “Save PNG copy” and PDF export remove them**; flattened blur is a pixelation, not a guarantee; markup on SVG images uses the image's own size. Sketches scale with their box (the drawing does not extend). Import: no OCR or handwriting recognition; legacy `.doc`, RTF, ODT, Markdown, and plain-text import are not supported; DOCX page layout (page size, columns, headers/footers, text boxes, fonts, comments, tracked changes, footnotes) is not reproduced, and pictures inside a paragraph are placed after it; PDF tables, columns, and reading order are not reconstructed and PDF pictures are not extracted; text of CJK PDFs may need character maps that are not bundled; the DOCX preview is a fresh conversion, not Word's layout; ZIP-bomb protection uses the sizes the ZIP declares (plus the 50 MB file limit and the worker); imports go to the Inbox, standalone notes, a section, or a project (not drag-and-drop onto a page).
- **Stage 4 slice 4 (PDF export):** one note per PDF (no notebook/project-wide PDF, no print-to-printer button; print the PDF). The PDF is not tagged (no document structure for screen readers; text is still extractable) and has no bookmarks. Layout follows the computer that exports (its fonts and line breaks); the embedded fonts are Liberation Sans and DejaVu Sans Mono, scaled per word to the on-screen widths, so letter shapes differ slightly from Segoe UI. Characters outside those fonts (emoji, CJK, and other scripts) and words in scripts that need shaping or right-to-left order are drawn as pictures (not searchable or copyable). Labels inside markup and sketches are part of the flattened picture (not searchable in the PDF). Page links are styled text (not clickable in the PDF); web links are clickable. Blurred areas are pixelated (not a security feature). Pictures are at most 200 dpi at their printed size and lossless (except unmarked JPEG photos), so notes with many screenshots make large PDFs (15 × 1200×800 → 8.7 MB). Tables taller than a sheet are split between rows where possible (no repeated header row); a single table row taller than a sheet is split between lines. Very narrow table columns wrap one character per line, exactly as on screen. Side-by-side text boxes can force a cut through content (reported; lines move whole to the next sheet). A text box is never scaled on its own: the whole note is scaled to its widest content. Export runs on the main thread except picture compression (a 1,000-line note takes ≈ 0.3 s here).
- **Stage 4 slice 5 (project export/import):** one project per package (no multi-project or notebook packages; templates are not included). **A package is not sanitized:** original images behind redactions, blur, and crops, and original DOCX/PDF files, are in it; there is no “export without originals” option. Reference pages come along as copies of what they were at export time; after import they are ordinary pages of the project (“Project copy”) and no longer references — the hidden-suggestions list is not carried over, and pins exist only when existing pages are linked on request. Only direct links are followed: a page linked only from a reference page is not included, and its link arrives unavailable. Links to pages that were not packaged (also pages in the Trash) arrive as unavailable links whose text is kept; the tooltip and the backup-restore warning describe them as deleted or not included. Linking to existing library pages is offered only in the workspace the package came from (same workspace ID, page ID, and creation time); in any other workspace a same-titled page is never matched, so a receiver may end up with their own page and a snapshot of the sender's page under the same title — and in the source workspace an imported snapshot and the still-suggested original appear side by side. Categories and tags are matched by name only. An import always stores its files again (no sharing with identical files already in the workspace), so importing the same project twice doubles its files. Imported records keep their original created/edited times. The import is one step with no undo: to remove an imported project, move it to the Trash and delete it forever (its notes go to the page Trash; its files stay stored, like those of any deleted page). A package must be used exactly as exported: one that was unpacked and zipped again is refused. **After the audit follow-up:** pages hidden for the project and pages of other projects are never packaged and there is no way to opt one in (proposal in `DATA_FORMAT.md`); a project that holds a stored “picture” which is none of the seven picture types cannot be exported until that picture is removed or replaced; a package from the earlier 0.4.2 build whose picture record names another type than its bytes is refused. File-content checks look at signatures, headers, and (for DOCX) the container — they do not decode pictures or parse PDFs, so a file that starts correctly but is damaged further in is accepted and simply shows as a broken picture or an unreadable original. SVG is recognized in UTF-8 and BOM-marked UTF-16 only. The strict ZIP reader accepts only what the app's own writer produces (no ZIP64, comments, extra fields, or data descriptors), which is also why repacked files are refused. Stage 5 adds Last edited / Manual sorting (see current checkpoint). Packages are built and read in memory, like backups; Stage 5 measures a project of approximately 258 MiB (see STAGE5_PERFORMANCE.md), and the 1 GiB / 128 MiB limits are safety limits, not measured capacities. There is no import of several packages at once, no drag-and-drop of a package onto the window, and no progress bar (only “Checking…” / “Importing…”). Imported projects sort by name, so “(imported 2)” is listed before “(imported)”. A package using a newer package/data format requires an updated app; format-4 packages migrate to format 5 as documented in DATA_FORMAT.md.
- **Archives (backups, Word documents, packages), after the second follow-up:** sizes recorded honestly but large are allowed up to the documented limits, so a small crafted backup can still make Restore unpack up to 4 GiB in all (deflate allows about 1032 : 1), and a crafted DOCX up to 300 MB, before the restore review or the import appears — slow and memory-hungry, but bounded, and nothing is replaced; forged sizes can no longer go past those limits. A backup with an unsafe path (or any name twice) is now refused instead of restored with a warning; so is a `records.json` over 512 MB (only possible with hundreds of millions of characters of mostly non-Latin text). Data descriptors are not read (the directory's sizes are used, as every reader does); an archive with data in front of its first entry whose offsets do not account for it, or with bytes after its end record, is refused as damaged. Only stored and deflate entries can be unpacked (a part in another compression method refuses a DOCX; in a backup, an unknown file in another method is simply ignored). A DOCX must still name its main part `word/document.xml` (unchanged); a DOCX with a damaged part CRC is now refused (the old check did not unpack anything). The Word-file check unpacks every part once (about 0.3 s for 32 MB here). fflate's writer still cannot write more than 65,535 entries (see “Second independent audit”).
- JavaScript bundle is ~1.19 MB (≈ 374 KB gzip) for the main app (project export/import added about 79 KB including both audit follow-ups; it is part of the main bundle so it works offline without a separate download), cached after the first visit; mammoth (~310 KB), PDF.js (~430 KB + 1.26 MB worker), and the PDF export code (~36 KB) with its fonts (≈ 2.3 MB) load only when used and are cached for offline use.
