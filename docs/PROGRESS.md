### Review fixes (0.1.1)
1. **Handover refused when work cannot be saved.** The editor freezes edits and saves before releasing; if saving fails it replies "refused", keeps the lock, and keeps editing with its changes intact. A thrown save error counts as a refusal. The requester only steals from a window that never acknowledges (frozen).
2. **Ownership enforced everywhere.** A stolen lock (or a commit refused by storage) makes the window read-only, cancels queued saves and retries, and stops backups. Storage now checks an owner token on every commit and restore, so stale retries from an old window are refused. Unsaved changes are held in memory with a banner: "Edit here and save them" (saved on top of the latest data) or "Discard them".
3. **Trashed pages of deleted sections.** Deleting a section/notebook moves its trashed pages' location to the Inbox. IndexedDB migration 1 → 2 repairs existing data; version-1 backups containing the orphan now restore (the page goes to the Inbox, with a warning). Live orphans are still rejected.
4. **Backups track revisions, not timestamps.** Each commit increments a stored revision in the same transaction; each snapshot records the revision it captured, read with the archived data. The interval uses a monotonic clock within a session; a clock set backwards counts as due.
5. Also found and fixed while testing: after taking editing back, the page could briefly reload without the edit that was mid-save (held edits are now saved before reloading, and in-flight saves are overlaid).

### Held-edit recovery fix (0.1.2)
The recheck of `0f28457` found that taking editing back replayed held changes as whole stale records (a body edit also carries its page record), which could revert a newer title or resurrect a trashed page's old live location in a deleted section (and then fail backup validation). Now:
- Held changes keep the stored version they were based on, and are **merged field by field** with the latest stored data. Only fields this window actually changed are applied; newer titles, locations, Trash state, and unrelated content are preserved.
- Conflicts (same field changed in both windows), edits to records deleted elsewhere, blocked deletions, and moves into deleted sections are **not applied in place**: they go to a new **"Recovered changes" page in the Inbox**, and a message says how many.
- Regression tests (`src/store/heldRecovery.test.ts`, 7, fully awaited — no timers): the two reported cases (rename in B; trash + delete notebook in B), same-text conflict, edit to a page deleted forever, conflicting rename, non-conflicting rename alongside B's new content, move into a deleted section. Each ends with a complete backup that passes validation and restores into a clean workspace with the expected result. The browser frozen-window test now also renames the page in B and checks A keeps B's title.

### Stage 2 data-safety review (0.2.1)
A focused review of shared references, project copies, archive/Trash/deletion, upgrade and backup compatibility, and two-window editing found four concrete defects. Each was reproduced first (isolated fake-indexeddb workspaces and, for the date field, real Chromium), fixed, and covered by a test that fails without the fix:
1. **A mistyped due-date year made every later backup unrestorable.** Chrome's date field produced `20261-12-15` for a five-digit year; the store accepted it and restore validation then refused the whole backup (“Project #1 is invalid”). Years 0001–0099 (Chrome gives `0099-12-15` for a two-digit year) were also wrongly treated as invalid because `Date.UTC` maps them to 1900–1999. Fixed: correct date-only check for all four-digit years; the store ignores invalid due dates (the previous date stays); the field has `max="9999-12-31"`, which caps the year at four digits in Chrome; and a backup that already contains an invalid due date (possible from 0.2.0) restores with that date cleared and a warning.
2. **A refused held project deletion still moved the project's notes to the Trash.** If window A deleted a project forever while it could not save, and window B then changed that project, taking editing back kept the project (correct) but applied A's “move notes to Trash” part, leaving a live project without its notes.
3. **A refused held category or tag deletion still removed it from every record.** If B renamed the category/tag meanwhile, it was kept but stripped from all notebooks, sections, pages, and projects.
4. **A refused held page deletion still emptied the page and cut its links.** If B renamed the page meanwhile, it was kept but its text boxes and images were deleted, its pins/hides in other projects were removed, and its project copies lost their source link. (The emptied-page part existed since Stage 1.)

Fix for 2–4: `withoutRefusedCascades` in `src/store/reconcile.ts` predicts which held deletions will be refused (with the same rules as before) and drops only the side effects that belonged to them, before anything is merged. Deletions that are not refused behave as before.

Checked and found sound (no change needed): shared-reference edits reaching every linked project; copy independence both ways; project deletion never touching library pages; deleting an original keeping its copy's text and image bytes (assertion added, through a full backup → clean restore); archive/Trash/restore record validity; Stage 1 database and backup upgrades; failed migration and invalid restore preserving the workspace; read-only windows refusing every Stage 2 change (test added); merges of unrelated changes and removal of dangling links.

**Open findings and their status after 0.4.1:**
1. **Persistent storage “Not granted”** (even after “Ask again”). *Investigated; documented; not changed.* This is Chrome's decision, made automatically and without a prompt (it weighs things like site engagement and whether the app is installed); `navigator.storage.persist()` cannot force it, and the app already reports the browser's real answer. **Consequences:** without it, Chrome may delete the whole site's data (every note, attachment, and setting) without asking when the disk is nearly full. With or without it, clearing site data, removing or resetting the Chrome profile, or opening the app at a different address or port (each has separate storage) loses or hides the workspace — only a backup folder or downloaded backup protects against those. **How the app communicates it today:** Settings → Storage shows “Not granted — under severe disk pressure the browser could clear site data. Keep regular backups.” with “Ask again” (whose refusal message says installing or regular use can change it); the always-visible backup pill shows “No backup folder” / “Backed up …” / “Backups paused” (warning style only for paused/missing folders). **Gaps:** the persistence state is only visible in Settings; “No backup folder” is not shown as a warning even when storage is not persistent; the Settings text does not say that Chrome decides on its own (so “Ask again” rarely helps) or that persistence does not protect against clearing data or profile loss. **Recommendation (needs the user's approval; not implemented):** show the backup pill in warning style, plus a one-time callout on Home, when storage is not persistent and no backup folder is connected (or the last backup is old); reword the Settings line along the lines above and suggest installing the app (Chrome menu → Install). The consequences are now also in `README.md` (“Backups — what to know”).
2. **Scanned PDF labelled “Imported draft … editable conversion”.** *Confirmed defect; fixed in 0.4.1.* A file kept without a conversion (scanned, damaged, or password-protected) now shows **“Original file only — not converted”**, says why it was not converted, that there is no converted text to edit (the page text is only an explanation), and that the original is unchanged (Preview / Download original). The conversion-notes list is not repeated. Such pages are recognised from the reason already stored as their first note (`isOriginalOnly`), so pages kept by 0.4.0 are relabelled too and no stored record changed. Covered by a unit test and the browser import test.
3. **Manual backup freeze** (an earlier automated run suggested ~30 s; the user's manual run did not reproduce it; duration not measured). *Not reproduced; not investigated further in this slice.* Backups are still built in memory (see Known limitations).
4. **Possible text loss after toolbar formatting during rapid editing** (preliminary report; repeated manual tests did not reproduce it). *Not reproduced; not claimed fixed.* The existing editor regression tests still pass; no new evidence was found.
5. **Older-workspace migration** (0.1–0.3 workspace upgraded to 0.4.x in real Chrome). *Not tested by the user or here.* Different localhost ports have separate browser storage, so the original workspace was never touched; it must not be modified or overwritten. Still on the manual list below.

### Stage 4 slice 4 — note-to-PDF export (0.4.1)
- **Export PDF** in every page header (Inbox, standalone notes, notebook pages, project notes, shared references, imported drafts), also in a read-only window (it only reads). A dialog builds the PDF on this computer and **previews the actual file** with PDF.js; options: Letter or A4 (default from the browser locale), automatic/portrait/landscape, light paper or dark as on screen (remembered per device). “Download PDF” saves `<title>.pdf`.
- **Faithful text:** real, selectable, searchable text in embedded subset fonts (Liberation Sans, DejaVu Sans Mono for code), laid out by the browser with the editor's own CSS, so lines break exactly as on screen. Headings, bold/italic/underline/strike, inline code and code blocks, bullet and numbered lists (markers included), quotes, tables (borders, header shading, spans), horizontal rules, web links (clickable), and page links (styled text) are kept. Words with characters the fonts lack (emoji) or scripts that need shaping (Arabic, Hebrew, Indic…) are drawn as small pictures by the browser and reported.
- **Pictures:** screenshots and photos with their **crop, annotations, blur (pixelated), and redactions flattened** by the same code as “Save PNG copy”; sketches drawn at up to 4× for sharpness. **Only the flattened pixels enter the PDF — never the stored original file — so redacted pixels and file metadata (EXIF/GPS) cannot leak.** Unmarked JPEG photos are re-encoded as JPEG from their pixels; everything else is lossless. Missing or unreadable image files become labelled placeholders.
- **Pagination:** one band of the note per sheet; cuts never go through a line of text or a picture that fits on a sheet (it moves whole to the next sheet, also when it does not fit under the title), prefer the space between objects and between paragraphs, avoid stranding headings and splitting table rows, and skip blank space (no empty sheets). Pictures taller than a sheet are split into exactly continuing pieces. First sheet: title, location, export time; every sheet: footer with the title and “Page n of N”.
- **Wide content:** the content width is fitted to the sheet (never enlarged, never shrunk to fit the height); automatic orientation picks landscape when portrait text would be under about 9 pt; tables wider than their box (which scroll on screen) are drawn in full and the page is scaled to fit. Overlapping objects keep their stacking order. If a text box needs more room than on screen, what is below it moves down so nothing is covered.
- **The dialog explains** sheets and text size, scaling, landscape choice, wide tables, flattened redactions, pixelated blur (not a secure redaction), split pictures, forced breaks, pictures for unsupported characters, missing images, page links, and that an imported draft's original is not included.
- **Nothing in the workspace changes** (verified in IndexedDB before/after); no stored record, backup, or migration changed (format 4 / DB 5). Works offline (code and fonts are in the offline cache).
- Code: `src/export/` (pure: `paginate.ts`, `layoutRules.ts`, `pdfWriter.ts`, `trueType.ts`; browser: `layoutNote.ts`, `notePdf.ts`, `markupRaster.ts`, `fonts.ts`), `src/ui/canvas/PdfExportDialog.tsx`. The PNG-copy flattener moved from `ui/canvas/markupExport.ts` to `src/export/markupRaster.ts` (unchanged behaviour; its browser test still passes) so the export layer does not depend on UI code.
- **Found and fixed while building it:** (1) word spacing looked uneven because glyphs were scaled per line — now each word is scaled to its own measured width; (2) a screenshot that fits on a full sheet was split (773 + 27 px) when it did not fit under the first sheet's title — it now starts on the next sheet whole; (3) a damaged image file would have aborted the whole export — it now becomes a placeholder; (4) right-to-left and shaped scripts would have been written unshaped — they are drawn by the browser; (5) unusual whitespace between words could have produced a missing-glyph box — it is written as plain spaces; (6) two existing browser tests failed on this machine before any change because its locale (en_CA) orders date fields year-first while the tests type US month/day/year — the Playwright browser now runs in en-US; (7) an existing browser test failed intermittently (2 of 10 runs on the untouched baseline commit): it pressed a sketch tool key before the markup editor had focused its drawing area, so the key reached the page title — the tests that draw by keyboard now wait for that focus (app behaviour unchanged; the window is one frame after the click, so it is unlikely to affect a person).

## Known limitations
- Stage 1 limitations still apply: held changes live only in that window's memory; no character-level text merge; opening a page can save re-measured text heights; undo is per page and in memory; no multi-select, guides, snapping, alt-text editor, or checklists; image bytes of deleted objects are kept; backups are built in memory; basic phone layout; folder backups need Chrome/Edge on a desktop and only run while the app is open; restore replaces the whole workspace.
- Project details, categories, tags, pins/hides, archive, and project trash are not in undo history (page Trash and project Trash cover deletion).
- Tags are on pages only (not on projects); categories are on projects, notebooks, sections, and pages.
- Search reads all stored text into memory and is rebuilt after each save; it has not been measured on the 1,000-page synthetic dataset (Stage 5). Original attachment contents are not searched — only their file names.
- Recently opened pages are per device (`localStorage`) and not in backups.
- Local file paths are copied, not opened (browsers cannot open arbitrary local paths). Dropbox links open in a new tab and need a connection.
- A project copy shares image bytes with the original (bytes never change, so the pages stay independent).
- Deleting a page forever also removes it from other projects' pins; there is no per-link history.
- An invalid due date already stored by 0.2.0 stays in this browser's workspace until the date is changed; restores clear it (with a warning).
- Two windows can each create a category or tag with the same name while one cannot save; both are kept (rename or delete one in Settings).
- In a held-edit merge, a pin in one window and a hide of the same page in the other both survive; the page then shows as pinned.
- **Stage 3:** task changes (moves, edits, deletes) are not in undo history; task deletion asks for confirmation and is permanent (no task Trash). Deleting a project forever deletes its tasks. Tasks have no recurring dates, reminders, notifications, time tracking, assignees, or calendar sync. Drag-and-drop is basic (drop on a card inserts before it; drop on a column appends) and was not browser-automated. Templates are snapshots: editing a template's content means saving a new one (rename/describe/delete only in Settings). A project template keeps file locations, equipment, and software but not customer, site, job number, contacts, dates, or task status. Template images reuse attachment bytes (never changed), like project copies. Task filters are per device (`localStorage`). Local paths are copied, never opened. Daily work logs are not built (optional later). Portable project export is Stage 4.
- **Stage 4:** Tables have no drag-to-resize columns (they size to the text box) and no cell colours; code blocks have no syntax highlighting or language label. Page links: a link to a page deleted forever stays (marked “deleted”) rather than being removed; links inside a project template still point at the original pages (not remapped to the new project's notes); backlinks are read when a page opens (not live); no page-title autocomplete inside the text beyond the picker. Markup: one editor at a time in a modal window; no multi-select, rotation, or snapping; text labels have no font choice; blur and redact areas always draw under other annotations; **the original image (and every backup) keeps redacted pixels — only “Save PNG copy” and PDF export remove them**; flattened blur is a pixelation, not a guarantee; markup on SVG images uses the image's own size. Sketches scale with their box (the drawing does not extend). Import: no OCR or handwriting recognition; legacy `.doc`, RTF, ODT, Markdown, and plain-text import are not supported; DOCX page layout (page size, columns, headers/footers, text boxes, fonts, comments, tracked changes, footnotes) is not reproduced, and pictures inside a paragraph are placed after it; PDF tables, columns, and reading order are not reconstructed and PDF pictures are not extracted; text of CJK PDFs may need character maps that are not bundled; the DOCX preview is a fresh conversion, not Word's layout; ZIP-bomb protection uses the sizes the ZIP declares (plus the 50 MB file limit and the worker); imports go to the Inbox, standalone notes, a section, or a project (not drag-and-drop onto a page).
- **Stage 4 slice 4 (PDF export):** one note per PDF (no notebook/project-wide PDF, no print-to-printer button; print the PDF). The PDF is not tagged (no document structure for screen readers; text is still extractable) and has no bookmarks. Layout follows the computer that exports (its fonts and line breaks); the embedded fonts are Liberation Sans and DejaVu Sans Mono, scaled per word to the on-screen widths, so letter shapes differ slightly from Segoe UI. Characters outside those fonts (emoji, CJK, and other scripts) and words in scripts that need shaping or right-to-left order are drawn as pictures (not searchable or copyable). Labels inside markup and sketches are part of the flattened picture (not searchable in the PDF). Page links are styled text (not clickable in the PDF); web links are clickable. Blurred areas are pixelated (not a security feature). Pictures are at most 200 dpi at their printed size and lossless (except unmarked JPEG photos), so notes with many screenshots make large PDFs (15 × 1200×800 → 8.7 MB). Tables taller than a sheet are split between rows where possible (no repeated header row); a single table row taller than a sheet is split between lines. Very narrow table columns wrap one character per line, exactly as on screen. Side-by-side text boxes can force a cut through content (reported; lines move whole to the next sheet). A text box is never scaled on its own: the whole note is scaled to its widest content. Export runs on the main thread except picture compression (a 1,000-line note takes ≈ 0.3 s here).
- JavaScript bundle is ~1.09 MB (≈ 342 KB gzip) for the main app, cached after the first visit; mammoth (~310 KB), PDF.js (~430 KB + 1.26 MB worker), and the PDF export code (~36 KB) with its fonts (≈ 2.3 MB) load only when used and are cached for offline use.
